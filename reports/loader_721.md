# 721 History loader idles without a heavy query (27 Nov 2026)
- What it was doing: every hour, even with all 289 owned months loaded, it pulled all 4.26 million loaded file names into memory and ran count(DISTINCT market_id) over bf_hist_other (280 million rows). It also left a database connection open every cycle. The process peaked at 5.4 GB, sat asleep at 3.3 GB plus 0.6 GB swap, and was OOM-killed at 4.2 GB on 26 Nov (kernel log, 19:44 CET). That query was still running when Postgres restarted at 06:47 CET today.
- What it does now: it reads the owned list from Betfair and checks it against bf_hist_months (264 rows). If nothing is left to load, it writes loader_idle.json (checked_at, to_load 0) and closes its connection. loaded_months.json holds each month's files and loaded counts and is rewritten only when that table changes. Then it sleeps 1 hour. A newly owned month still goes to the loading path, and only that month is loaded (tested with a dummy Tennis 2019-01 that stopped before any download). The loading path now uses the planner's row estimate, not a full distinct count.
- Before / after, one idle cycle: before, 5.4 GB peak, 3.3 GB held while asleep, about 15 GB of Postgres temp files, and a run time of hours. I did not re-time it because the trial loop was running at 5.4 GB. After: 1.5 s, 40 MB peak, 0 temp files, 0 temp bytes (pg_stat_database unchanged).
- Loaded months unchanged: bf_hist_months has 264 rows, md5 f1a1217c1b7509ea853d53e7f60260c1 before and after, and bf_hist_other_files has 4,261,386 rows before and after.
- Integrity suite, job 357 copy and WATCHMAN.md: 'nothing to load', checked in the last 2 h, now reads as PASS. An idle file older than 2 h, or months still to load, still FAILs. All 5 test cases passed. Backups are *.bak_721.
